### Step 1 — Baseline and contracts — complete 2026-09-28

- Agent/model/reasoning: Codex / GPT-5.6 Terra equivalent / medium.
- Scope completed and files changed: Reviewed the focused Tkinter exercise tabs, language registry/data modules, and SQLite review store. Added this baseline and the agreed contracts to `runbook.md` only; application code and existing learner data were not changed.
- Tests and manual checks, with results: `python -m pytest -q` -> `10 passed, 176 subtests passed` in 0.29s. No GUI mutation was made, so no new manual GUI check was needed.
- Current exercise-flow baseline:
  - Flashcards prompt target language -> English. A typed answer is scheduled on every check; Reveal records one incorrect attempt for that displayed item, although later checks are still independently recorded.
  - Conjugation drills prompt a present-tense target-language verb form for a pronoun. The prompt uses the displayed phrase as its current review key. Show answer records at most one incorrect attempt per displayed pronoun; repeated checks can still record additional attempts.
  - Sentence practice prompts target language -> English, selects from curated and optionally generated sentences, and records a Reveal once per displayed sentence. Existing generated sentence IDs are random and therefore are not suitable as durable learning IDs.
  - Flip cards use learner self-ratings for target-language vocabulary or sentences. Review presents currently due queue rows as multiple-choice checks and reschedules them through the same callback.
  - `LangPracticeApp` starts one SQLite session per launch, routes tab callbacks through `_on_attempt`, and loads due rows only for the active language. Switching the Language menu rebuilds tabs and persists `cache/settings.json:last_language`; queued review rows already carry a language and are queried separately.
- Existing review-schema baseline: `sessions(session_id, started_at, ended_at)` holds only launch timing. `review_queue` holds one mutable row per `item_key` (`language`, displayed exercise name, prompt, correct answer), plus the latest user answer, mastery, lapses, due time, and last-seen time. It is a scheduler state, not an attempt log; it cannot say whether an earlier answer was first-try, helped, revealed, or skipped.
- Decisions and data/interface contracts (to be implemented in Steps 2–5):
  - IDs are semantic and immutable, never derived from a tab label or the rendered wording. `language` is a registered module key. `exercise_id` identifies a presentation (`flashcard`, `conjugation`, `sentence`, `flip_card`, or `review`); `skill` identifies what is measured (`vocabulary`, `verb_form`, `sentence_translation`, or `card_recall`); and `direction` identifies the requested recall (`target_to_english`, `english_to_target`, `target_form`, or `self_rating`). New values require an explicit migration/contract update.
  - Content supplies a stable `item_id`: vocabulary uses a language-scoped authored vocabulary ID; a verb form uses a language-scoped form ID composed from authored infinitive ID, tense, and canonical person; curated sentences use their language-scoped authored sentence ID. Generated sentences may retain a content-derived ID for diagnostics, but are excluded from guided readiness until they have validated authored target metadata. IDs remain stable if display text, punctuation, or UI labels change.
  - The append-only `AttemptEvent` contract is: `event_id`, UTC `occurred_at`, `session_id`, `language`, `exercise_id`, `skill`, `direction`, `item_id`, `outcome` (`correct`, `incorrect`, or `skipped`), `first_try`, `support_used` (a set/flags including `hint` and `reveal`), and optional submitted `answer`. A revealed or assisted response is not an unaided first-try success. One learner resolution of one displayed prompt emits at most one event; UI retries before resolution are tracked in memory so they cannot double-count it.
  - A persistent `ReadinessSnapshot` is a derived/cacheable view keyed by `(language, skill, direction, item_id)`. It contains only aggregate evidence needed for decisions (unaided first-try successes/attempts, assisted/revealed attempts, recent misses, last-attempt time, and separately maintained due state). It is recomputable from new attempt history and never treats a single same-day success as lasting proficiency.
  - `SessionState` is ephemeral and keyed by the launch `session_id`: session start/end, active language context, goal/pacing, new-item count, current prompt resolution guard, and recent misses/help use. It informs the current session only; attempt history and readiness snapshots remain the cross-launch source of truth. A single session can contain events from more than one language, so language belongs on every event and snapshot key.
  - A pure planner returns `PlannerRecommendation(destination_exercise_id, skill, direction, item_id | None, support_level, reason)`. `reason` is a concise learner-readable explanation, not an internal code. The planner may recommend, never lock the learner out of a focused tab, support choice, skip, or ending early.
- Migration approach: Step 2 will use an idempotent, transactional schema version/migration record. It will retain every existing `sessions` and `review_queue` row and preserve their due scheduling behavior. Pre-history queue rows become `legacy scheduling evidence` with unknown detailed proficiency: do not synthesize `AttemptEvent` rows, first-try results, hints, reveals, skips, answers, or inferred timestamps from them. New append-only events begin only after migration; due state is maintained separately from that history. Migration tests must open a representative old-schema database, rerun migration safely, verify French/Italian isolation, and prove existing due rows remain usable.
- Issues, risks, and possible corrections: The current callback accepts only rendered prompt/answer strings, and the current content does not consistently own vocabulary or conjugation-form IDs. Step 2 must introduce the durable model/database boundary before Step 3 rewires UI callbacks. Steps 3 and 4 must preserve direct practice while adding prompt-resolution guards and authored content metadata.
- Acceptance criteria: passed. Contracts and migration behavior are documented; current tests pass; no broad refactor was introduced.
- Next step's starting point: Implement the durable IDs, append-only attempt history, snapshots/due-state separation, and idempotent SQLite migration in `lang_practice/models.py` and `lang_practice/review_db.py`, with migration tests. Preserve legacy queue rows exactly as scheduler data with unknown detailed proficiency.
